# L4: source tree setup for `lineage-24.0`

Prepared 2026-10-09 by the lead. Tree location decided by the owner: **alongside** the 23.2 tree on the external
drive.

## Summary

1. Tree goes to `/mnt/build/lineage-24`, bind-mounted at `~/android/lineage-24`. Mounts are manual, redo both
   after every reboot.
2. `git-lfs` 3.6.1 and `repo` launcher 2.65 are already installed, so `repo init --git-lfs` will work.
3. Base pin to record after init: `LineageOS/android@lineage-24.0` = `2a50ca061bffe` (2026-09-30, "manifest: Track Canvas").
4. Expect ~150 GB source. With `out/` later (~300 GB) the drive reaches ~796 GB of 916 GB.
5. **Never** share `out/` with the 23.2 tree. Do not touch `~/android/lineage`.

## 2. Mounts (repeat after every reboot, neither is in `/etc/fstab`)

```bash
sudo mount /dev/sda /mnt/build
sudo mount --bind /mnt/build/lineage ~/android/lineage      # 23.2 tree, for reference
```

**The 24.0 tree needs no bind mount.** `/mnt/build` is owned by `anton` and writable without sudo, so the
24.0 tree lives *directly* at **`/mnt/build/lineage-24`**. This was a deliberate change from the original
plan (§9.1): it needs no `sudo`, survives a reboot with one command instead of two, and removes a
class of "bind mount missing, build writes to the wrong place" failure. The 23.2 tree keeps its bind mount
because it predates this and its path is referenced in 23.2-era notes.

So after a reboot, only one command is needed for the 24 tree: `sudo mount /dev/sda /mnt/build`.

The cost is a longer path in build logs (`/mnt/build/lineage-24/...` instead of `~/android/lineage-24/...`).
Nothing in the build cares; both are real paths with no spaces or symlinks.

## 3. repo init

```bash
mkdir -p /mnt/build/lineage-24
cd /mnt/build/lineage-24
~/bin/repo init -u git@github.com:LineageOS/android.git -b lineage-24.0 --git-lfs --no-clone-bundle
```

**Use the SSH URL, not https.** The LineageOS manifest declares its GitHub remote as
`<remote name="github" fetch=".." .../>` — a *relative* URL, which inherits the scheme and host from whatever
`repo init` was given. Init over SSH and every project fetches over SSH. Init over https and they all fetch
over https, which is what fails later when a push is attempted.

`--git-lfs` requires `git-lfs` on PATH (3.6.1 ✅). `--no-clone-bundle` avoids the giant bundle fetch.

## 4. Manifests

```bash
DOCS=~/Downloads/Github_codes/lineageos-galaxy-tab-s5e
mkdir -p .repo/local_manifests        # NOT created by repo init
cp $DOCS/local_manifests/24/*.xml .repo/local_manifests/
```

All three manifests are copied, including LTE. Two tiny repos is much cheaper than a second
`repo sync` later. Copying the LTE manifest does **not** commit us to building LTE: that stays blocked
on L9's radio@1.4 decision. Build Wi-Fi first.

`repo manifest -r` does **not** work before the first sync. It shells out to git inside project
directories that do not exist yet, so it dies with
`FileNotFoundError: '/mnt/build/lineage-24/android'`. That is expected, not a broken manifest.
Verify the result *after* the sync instead (§7).

## 5. repo sync

```bash
cd /mnt/build/lineage-24
repo sync -c -j4
```

`-c` fetches only the current branch. `-j4` is also the manifest's own default
(`<default ... sync-j="4"/>`), so it is belt and braces. Expect several hours and ~150 GB.

Run it in a clean shell with `USE_CCACHE` unset (TASKS-L24 §0.8 — changing that later forces a full rebuild).
Note `repo`'s progress output is block-buffered when stdout is not a terminal, so **the log file stays empty
for minutes at a time even while the sync is progressing**. Judge progress by directory growth
(`ls /mnt/build/lineage-24`) and by the `.repo/projects` count, not by the log.

I ran it as:

```bash
nohup env -i HOME=$HOME USER=$USER PATH=/usr/local/bin:/usr/bin:/bin LANG=C.UTF-8 \
  bash --noprofile --norc -c \
  'unset USE_CCACHE; cd /mnt/build/lineage-24 && ~/bin/repo sync -c -j4' \
  > ~/work/l24-sync-20261009.log 2>&1 &
```

Log on the internal disk (`~/work`, text only) so a full drive cannot stall the sync.

## 6. Record the pins (do this immediately after sync)

```bash
cd /mnt/build/lineage-24
git -C .repo/manifests rev-parse HEAD                       # expect 2a50ca061bffe...
repo status | grep -E 'gts4lv|sdm670|hardware/samsung' > ~/work/l24-pins-20261009.txt
```

`lineage-24.0` is pre-release and moving (`frameworks/base` took 165 commits in the 30 days to 2026-10-09).
Recording these SHAs is what makes the tree reproducible and tells us later what a re-sync would actually change.
Move the base with **targeted** `repo sync -c <project>` calls, never a blanket sync.

## 7. Post-sync checks

```bash
cd /mnt/build/lineage-24
repo sync -c -j4                       # second pass: catches partial clones
test -d kernel/samsung/sdm670 && echo "kernel present"
git -C kernel/samsung/sdm670 log --oneline -1     # expect 500658be3c16 (same as 23.2)
git -C device/samsung/gts4lv-common log --oneline -1  # expect 1188e2b14a5a
git -C device/samsung/gts4lv-common remote -v | head -1   # must be git@github.com, not https
grep -rn 'target-level' device/samsung/gts4lv-common/manifest.xml   # still "5": L6 lives on port/l24-dt-1
```

Both forks should report the *same* SHA as their 23.2 counterparts. If not, L5's push did not land as intended.
The device tree is still `target-level="5"` on `lineage-24.0`: the L6 port commits are on `port/l24-dt-1`
and must not be merged into `lineage-24.0` (TASKS-L24 §0.3).

## 8. What L4 deliberately does not do

- **No L6 port commits yet.** The device tree stays at `1188e2b` (`target-level="5"`, `disable_configstore`
  still referenced) until `port/l24-dt-1` exists. Syncing first and porting second means one sync; the reverse
  means two.
- **No first build.** That is L7, and it needs the device tree ported first.

## Problems

1. **`.repo/local_manifests/` is not created by `repo init`.** The `cp` fails with
   `target '.repo/local_manifests/': No such file or directory`. Create it first. Fixed in §4.
2. **`repo manifest -r` cannot be used as a pre-sync check** (§4). Use the post-sync checks in §7.
3. **The sync log stays empty for minutes at a time** because `repo` block-buffers when stdout is not a
   terminal. This looks like a hang and is not one. Track progress by directory growth instead.
