# D1: ship only the Lineage AIDL health HAL

Device-tree fix, branch `port/l24-dt-5` @ `647daf4`, cut from the device fork's `lineage-24.0`
(`c2fe044`, which already contains the L6/L7 port work). One commit, one file.

Found during an owner-directed debugging session on 2026-10-12 on a tablet running the **23.2**
release build. Not part of the 24 boot sequence, so it does not gate L8/L10.

## 1. Finding

`gts4lv.mk` shipped **two** health HAL implementations, and the wrong one won:

```make
PRODUCT_PACKAGES += \
    android.hardware.health-service.samsung \      # line 160
    android.hardware.health-service.samsung-recovery
...
PRODUCT_PACKAGES += \
    vendor.lineage.health-service.default          # line 169
```

On the booted tablet both processes were alive, parented to init:

```
1098  android.hardware.health-service.samsung
1119  vendor.lineage.health-service.default
```

Only the blob ever registered the service. From logcat at boot:

```
servicemanager: Caller(pid=1098,uid=1000,sid=u:r:hal_health_default:s0) Found
    android.hardware.health.IHealth/default in device VINTF manifest.
```

PID 1119 never appears in any servicemanager line. `dumpsys android.hardware.health.IHealth/default`
returns `FAILED_TRANSACTION`.

## 2. Consequence

`vendor.lineage.health-service.default` is what implements Lineage's **charging control**. The same
`gts4lv.mk` configures it (`gts4lv.mk:171-184`):

```make
$(call soong_config_set,lineage_health,charging_control_charging_path,/sys/class/power_supply/battery/batt_slate_mode)
$(call soong_config_set,lineage_health,fast_charge_node,/sys/class/sec/switch/afc_disable)
```

Because it could not register `IHealth/default`, that feature was **silently dead** — the Settings
toggle would exist and do nothing. The device tree also carries sepolicy for the Lineage domain
(`sepolicy/vendor/hal_lineage_health_default.te:1`), so it clearly intended the Lineage HAL to run.

This is **not** the cause of the charging-notification problem reported alongside it (see
`analysis/l24/D2.md`'s sibling investigation notes in `WORKLOG`; the notification work is separate
and still open).

## 3. The decision and why this direction

The blob is removed, not the Lineage HAL. The deciding argument is build safety under the
"no build in this task" constraint:

- `vendor.lineage.health-service.default` provides the **`lineage_health` Soong config module**,
  declared at `hardware/lineage/interfaces/health/aidl/default/Android.bp`. The eleven
  `soong_config_set` calls at `gts4lv.mk:171-184` read that module.
- Removing that package would leave eleven `soong_config_set` calls with no consumer. That is a
  plausible build failure that **cannot be checked without running a build**, which this task
  deliberately does not do.
- The blob has no other reference anywhere in the tree: `grep -rn "health-service.samsung"` over
  the device tree returns only `gts4lv.mk:160-161` — no init rc, no VINTF entry, no recovery root.

So the removal direction is chosen by which side is safe to remove unverified, not by preference.

Reference-tree support for keeping the Lineage HAL:
`analysis/reference-trees/exynos9810-common-22.2-to-23.2.tsv` shows `503ffa8` "Use bool Soong
config for charging bypass" and `c837cad` "overlay: Enable battery cycle count" — i.e. Lineage's own
health HAL plus Soong config is the convention on the sibling Exynos trees.

## 4. Confidence

**Medium.** The registration loss and the dead feature are directly observed. The claim that the
Lineage HAL is *sufficient* is inferred from the reference trees and has **not** been verified on
this device — see below.

## 5. Not verified / risks for the reviewer

1. **No build was run.** Per the owner's instruction, the fix is committed but unbuilt.
2. **Vendor-only battery properties.** The Samsung blob may populate fields the generic Lineage HAL
   does not map. `drivers/battery_v2/sec_battery.c` exports no `POWER_SUPPLY_CYCLE_COUNT` attribute
   (grep for `CYCLE_COUNT` returns nothing), so battery cycle count likely does not work either way —
   but this needs confirming on device, not assumed.
3. **Charging-control behaviour is untested.** After this change
   `vendor.lineage.health-service.default` should own `IHealth/default` and charging control should
   become live for the first time. That feature has therefore **never been tested on this device**.
   Treat a first failure there as "untested feature", not "regression introduced here".
4. **23.2 backport.** The identical file content is on `lineage-23.2` (the running build has the same
   duplicate). This commit targets the live 24 branch only. Port to 23.2 only if 23.2 maintenance
   resumes.
