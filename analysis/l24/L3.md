# L3: Android 17 changes that hit legacy devices

## Summary
1. netbpfload's kernel gates (23.2→24.0) are all satisfied by our `ro.bpf.kver_override=5.15.178`; two gates got stricter (5.10 now fatal, new 5.15 gate at API 37.1) — `7c04d866538e`.
2. `cgroups_28.json` / `cgroups_30.json` / `cgroups.json` and the vendor-override read order are **byte-identical** to 23.2, so fix `a7f1483` still applies; LineageOS re-added schedtune support on 24.0 (`e798488a4840`).
3. `/metadata/aconfig` is still required and is now created at **early-init** (new), on top of post-fs.
4. lmkd 24.0 drops the `pidfd_supported` fallback (pidfd_open now mandatory — we have it), makes PSI mandatory (already true for us) and `/proc/<pid>/status` `RssAnon:` mandatory (we have it); `process_mrelease` is still only optional and we still lack it.
5. `soong_config_set_bool,libion,legacy_impl,true` exists in 24.0 (`abd899da1a42`) and `device/lineage/sepolicy/libion` exists (`6b12f7181eeb`, 40 files); bionic/ART 24.0 add **no** unconditionally-used syscall; Gerrit: 226 hits / 168 merged.

Facts only. Interpretation is the strong model's job.

## 1. Connectivity BPF: what netbpfload requires of the kernel

### 1.1 How the version is read (and why our override is what counts)

* `bpf/headers/include/bpf/KernelUtils.h:39` @ `7c04d866538e` —
  `int kver_override_len = __system_property_get("ro.bpf.kver_override", kver_override);`
* `KernelUtils.h:40-42` — if the property is non-empty it is parsed instead of `uname().release`:
  `sscanf(kver_override_len > 0 ? kver_override : buf.release, "%u.%u.%u", ...)`.
* `KernelUtils.h:55-57` — for APEX code the compile-time minimum is 0, so all checks are real runtime checks:
  `static constexpr unsigned minSupportedKernelVer = / #ifdef __ANDROID_APEX__ ... KVER(0, 0, 0);`
* `bpf/loader/NetBpfLoad.cpp:116` @ `7c04d866538e` —
  `static_assert(!minSupportedKernelVer, "NetBpfLoad must not assume min kver");`
* `bpf/loader/NetBpfLoad.cpp:105` — `static_assert(__ANDROID_API__ == 31, "NetBpfLoad must be compiled for 31/S");`
  and `bpf/loader/Android.bp:76` — `min_sdk_version: "31"`.
  **New in 24.0:** 23.2 had `min_sdk_version: "30"` (`c23/bpf/loader/Android.bp:62`) and
  `static_assert(__ANDROID_API__ == 30, ... "for 30/R")`.

So netbpfload evaluates every gate below against the value of `ro.bpf.kver_override`
(5.15.178 for us), not against the real 4.9.337 kernel.

### 1.3 Which SDK level turns those gates on

* `bpf/headers/include/bpf/BpfUtils.h:150-161` @ `7c04d866538e`:
  `isAtLeast25Q2 = (api_level_full >= 3600)`, `isAtLeast25Q4 = (api_level_full >= 3610)`,
  `isAtLeast26Q2 = (api_level_full >= 3700)`, `isAtLeast26Q4 = (api_level_full >= 3710)`.
* `api_level_full` comes from `ro.build.version.sdk_full` (`BpfUtils.h:96-146`).
* AOSP `platform/build/release` @ `refs/tags/android-17.0.0_r1` (what `lineage-24.0/default.xml:34` pulls for `build/release`):
  `release_config_map.textproto` aliases `aosp_current` → `cp2a`; `flag_values/cp2a/RELEASE_PLATFORM_SDK_VERSION_FULL.textproto` = `"37.0"`;
  `flag_values/bp2a/...` = `"36.0"`. Our 23.2 build reports `ro.build.version.sdk_full=36.1`
  (`~/android/lineage/out/target/product/gts4lv/system/build.prop:33`).
  So 24.0 should be 37.0 or 36.x → `isAtLeast26Q4` (needs 37.1) is expected to be **false**,
  `isAtLeast25Q4` expected **true**. confidence: medium — L7 must confirm the value in the built image.

  (min kver 5.15, no upper bound): 5.15.178 passes.
* `bpf/progs/clatd.c:250,260` — min kver 4.14; `clatd.c:255,265` — 4.9–4.14 only (skipped at 5.15).
* **Removed in 24.0:** the `cgroupskb` ingress/egress stats programs

  and `... egress_stats, ...`); `grep -rn "cgroupskb" packages/modules_Connectivity` @ `7c04d866538e` → no hits.

### 1.5 Other new 23.2→24.0 items in netbpfload

  (`__INTRODUCED_IN(38)`, `libc/include/sched.h`, `libc/libc.map.txt`) plus private
  `__bionic_clone3` (`libc/arch-arm64/bionic/__bionic_clone.S`, and arm/x86/x86_64/riscv64).

  Nothing inside libc calls it: `pthread_create.cpp:491` still uses
  `clone(__pthread_start, child_stack, flags, ...)` and `fork.cpp:41` uses

* **mseal** — bionic 24.0 only exports the wrapper: `libc/include/sys/mman.h:234`
  `int mseal(...) __INTRODUCED_IN(36);`, `libc/libc.map.txt:1617`, `libc/SYSCALLS.TXT:135`.
  **This is identical in 23.2** (`bionic23/libc/include/sys/mman.h`, `libc.map.txt:1614`), and there is
  no internal caller: `grep -rn mseal android_bionic | grep -v 'kernel/uapi\|/tests/\|libc.map.txt'`
  hits only the header, `legacy_32_bit_support.cpp:165-166` (32-bit stub) and `SYSCALLS.TXT`.
* **process_madvise / pidfd_getfd / landlock** — wrappers only, unchanged from 23.2
  (`libc/include/sys/mman.h:171`, `libc/include/sys/pidfd.h:67`, `bits/glibc-syscalls.h:534-541,801-802,852-853`).
* **pidfd_open / pidfd_send_signal** — `pidfd_open` is used by ART in both versions
  (`libartbase/base/pidfd.h:35,38` @ `747707d6ce1c` and @ `18ea424e1026` — file md5-identical),
  and by lmkd 24.0 unconditionally (see §3.2).
* **MADV_\*** — the set used by ART is unchanged 23.2→24.0:
  `MADV_DONTNEED` (29 uses), `MADV_WILLNEED` (9 → 7), `MADV_FREE` (6), `MADV_DONTFORK` (4).
  No `MADV_POPULATE*`, no `MADV_COLLAPSE` in either tree (`grep` → 0).
* **Only new syscall in ART 24.0**: `perfetto_hprof/perfetto_hprof.cc:1202-1219` @ `747707d6ce1c`

```cpp
bool IsChromiumSeccompSandbox() {
  errno = 0;
  auto r = syscall(__NR_seccomp, SECCOMP_GET_ACTION_AVAIL, 0u, nullptr);
  return r == -1 && errno == EPERM;
}
```
  It is used only to skip a Perfetto heap dump (`DumpPerfetto`, `perfetto_hprof.cc:1217`).
  Any error other than `EPERM` (including `ENOSYS`) means "not a Chromium sandbox", i.e. the old behaviour.
  Our kernel has `__NR_seccomp` (`unistd.h:705-706`, `CONFIG_SECCOMP=y` at
  `arch/arm64/configs/gts4lv_eur_open_defconfig:544`) but not `SECCOMP_GET_ACTION_AVAIL`
  (4.14 feature) — by the code above that just yields "not chromium".
* Also new in bionic 24.0 but not a syscall: `clone.cpp` includes `<arm_sme.h>` (`clone.cpp:30-32`)
  and calls `__arm_za_disable()` on aarch64 (`clone.cpp:85-88`) — an SME/ZA build-time
  feature of the NDK headers, no kernel support involved.
