### 6.1 Why `gnss@1.1` does not fail, and why the override trick does not work here

- libvintf's device-manifest check does **not** compare HIDL versions against the framework matrix. `HalManifest::checkCompatibility()` for `SchemaType::DEVICE` only checks the sepolicy version and the kernel (`system/libvintf/HalManifest.cpp:491-520`), called from `VintfObject::checkCompatibility` (`system/libvintf/VintfObject.cpp:696`, manifest check at `:725-731`). There is no "declared version must be inside the FCM range" rule anywhere in libvintf.
- The only version-aware check is `checkUnusedHals` (runs because level 7 ≥ `Level::R` — `check_vintf.cpp:439-442`), and `HalManifest.cpp:386-404` forgives a manifest instance when a *child* interface of it is listed in the matrix. HIDL metadata says `gnss@2.0`/`2.1` inherit from `gnss@1.1`, and level 7 lists `gnss@2.0-2.1` → forgiven. Same mechanism forgives `soundtrigger@2.2` (child 2.3 is listed) and `radio@1.4` (child 1.5 is listed) and `radio@1.2::ISap` (listed).
- `checkDeprecation` (`VintfObject.cpp:977-1056`) compares the served HALs against the *older* FCM files (level 5 and 6 here) and reports anything the target level no longer allows. Level 6 lists `gnss 2.0-2.1`, `soundtrigger 2.3`, `radio 1.5-6`/`1.2` — all still allowed at level 7 → nothing deprecated. (Level 5's file is empty by design: `hardware/interfaces/compatibility_matrices/compatibility_matrix.5.xml:1-7` "Android R FCM has been deprecated, but this file is kept to help manage the android11-5.4 kernel config requirements". So today, at level 5, almost nothing is enforced at all.)
- **The override semantics**: `HalManifest::add()` (`system/libvintf/HalManifest.cpp:219-243`) removes, for an `override="true"` entry, all previously added HALs with the same name and the same **major** version as each of its `<version>`/`<fqname>` entries (and erases the HAL completely if the entry has no instances at all). So sm7125's `configs/manifest.xml` works because those HALs are declared in *other `DEVICE_MANIFEST_FILES`*, which `assemble_vintf` merges in order (`build/soong/android/vintf_data.go:115-131`).
- **A blob *fragment* cannot be overridden that way.** Merge order is `manifest.xml` first, then `vendor/etc/vintf/manifest/*` (`VintfObject::fetchDeviceHalManifest`, `VintfObject.cpp:316-357`), in raw `readdir` order, not sorted (`FileSystem.cpp:43-59`). Measured on a synthetic vendor tree with our real gnss fragment plus a device-tree override:
  - override in `manifest.xml` → `Cannot add manifest fragment …: HAL "android.hardware.gnss" has a conflict: Conflicting FqInstance: @2.1::IGnss/default (from …/manifest.xml) vs. @2.1::IGnss/default (from …/android.hardware.gnss@2.1-service-qti.xml)`, exit 70;
  - override as a fragment → same error when `readdir` happens to return the override first, and the outcome depends on `readdir` order, which is not guaranteed. **Not usable.** confidence: high

### 6.2 What the closest reference tree does (evidence for "leave it alone")

sm7125 is at `target-level="7"` on 24.0 (`configs/manifest.xml:1` @ `6edc6f2518c5`) and keeps **all three**:

- `soundtrigger@2.2` in its device manifest (`configs/manifest.xml:83-92`, no `override`) and `android.hardware.soundtrigger@2.2-impl` in `common.mk:82` @ `lineage-24.0`;
- the identical gnss blob fragment with `<fqname>@1.1::IGnss/default</fqname>` (`proprietary/vendor/etc/vintf/manifest/android.hardware.gnss@2.1-service-qti.xml` @ `lineage-24.0` in `TheMuppets/proprietary_vendor_samsung_sm7125-common`), and **no** gnss entry in its device manifest;
- `radio` is the one it *did* override (two blocks, `override="true"`, first empty then `@1.2::ISap` + `@1.5::IRadio`).

So an official FCM-7 LineageOS build ships `gnss@1.1` and `soundtrigger@2.2`. Our three findings are therefore **not** what stands between 23.2 and FCM 7. confidence: high

### 6.3 Soundtrigger alternative: ship 2.3 instead of dropping

`hardware/interfaces/soundtrigger/2.3/default/Android.bp:26` defines `android.hardware.soundtrigger@2.3-impl`, and the audio service prefers 2.3 (`service.cpp:118`), so switching `PRODUCT_PACKAGES` to `android.hardware.soundtrigger@2.3-impl` + declaring `2.3` would satisfy FCM 7 and keep the hardware hotword path. **Not recommended without testing:** `SoundTriggerHw::getProperties_2_3` calls `mHwDevice->get_properties_extended()` (`hardware/interfaces/soundtrigger/2.3/default/SoundTriggerHw.cpp:780`), a function pointer in the blob's `sound_trigger_hw_device` struct that is only valid for `SOUND_TRIGGER_DEVICE_API_VERSION_1_3`+ (`hardware/libhardware/include/hardware/sound_trigger.h:160-168`). If the sdm710 blob does not provide it, the audio HAL service would fault at startup. A blob from an SM8350 phone very likely has it, but that cannot be proven without the tablet. confidence: low (needs an L8 boot test)

## 7. `PRODUCT_OTA_ENFORCE_VINTF_KERNEL_REQUIREMENTS` — why we do not need sm7125's flag *yet*

- FCM 7 declares `<kernel version="4.14.336" level="7">` requirement blocks (built copy: `out/target/product/gts4lv/system/etc/vintf/compatibility_matrix.7.xml:811`, generated from `hardware/interfaces/compatibility_matrices/compatibility_matrix.7.xml`). Our kernel is **4.9.337** (`kernel/samsung/sdm670/Makefile:1-5` @ `500658be3c16`; `ro.bpf.kver_override=5.15.178` in `device/samsung/gts4lv-common/product.prop:7` only affects bpfloader). With `--kernel` supplied, `checkvintf` fails: `No kernel entry found for kernel version 4.9 at kernel FCM version 7. The following kernel requirements are checked: Minimum LTS: 4.14.336 … 5.15.41 …` (verified).
- But the build does **not** pass `--kernel` to us: `android_device.go:2033-2036` adds it only when `a.kernelVersion != nil`, which requires the soong boot-image kernel provider (`getKernel`, `:1716-1723`); our kernel is built by the legacy `TARGET_KERNEL_SOURCE` path (`device/samsung/gts4lv-common/BoardConfigCommon.mk:103`), so it is nil. Proof from our own build log: `out/target/product/gts4lv/obj/PACKAGING/check_vintf_all_intermediates/check_vintf_compatible.log:46` shows the args with no `--kernel`.
- The target-files (OTA) check skips the kernel too: `build/make/tools/releasetools/check_target_files_vintf.py:98-107` only passes `--kernel` when `META/kernel_version.txt` exists, and there is no such file in our target-files (`…/lineage_gts4lv-target_files/META/`), because `PRODUCT_OTA_ENFORCE_VINTF_KERNEL_REQUIREMENTS` defaults to unset: `build/make/core/product_config.mk:527-532` only defaults it to `true` when `PRODUCT_SHIPPING_API_LEVEL ≥ 29`, and ours is **28** (`device/samsung/gts4lv-common/gts4lv.mk:18` → `build/make/target/product/product_launched_with_p.mk:2`, still 28 on 24.0 — fetched `product_config.mk:527-530` and `product_launched_with_p.mk` from `lineage-24.0`).
- **Watch item for L6/L7:** if anything in the 24 port raises the shipping API level to ≥ 29, or if the kernel moves to the soong path, the flag becomes load-bearing and we must copy sm7125's `PRODUCT_OTA_ENFORCE_VINTF_KERNEL_REQUIREMENTS := false` (`common.mk:26` @ `lineage-24.0`, commit `1d2a05927c04d4537c5a24506c91dc767bf3fdb8`, "sm7125-common: Disable PRODUCT_OTA_ENFORCE_VINTF_KERNEL_REQUIREMENTS"). Note the make-side flag only affects the target-files/OTA check; the build-time soong check has a TODO for it (`android_device.go:2046`).

If the model prefers strictness: gnss = remove `android.hardware.gnss@2.1-service-qti.xml` from `vendor/samsung/gts4lv-common/gts4lv-common-vendor.mk:456` **and** declare `@2.1::IGnss/default` in `device/samsung/gts4lv-common/manifest.xml` (verified COMPATIBLE; needs a vendor-repo branch, not just a device-tree commit). soundtrigger = delete `manifest.xml:102-110` + `gts4lv.mk:54` (verified COMPATIBLE; loses the hardware hotword path).
4. `radio@1.4` stays open → L9. It is not a build blocker; it is a CTS/VTS and future-Telephony question.

## Problems

None. Two things cost time and are worth knowing: (a) `readdir` order of `vendor/etc/vintf/manifest/` is unsorted, so a `vintf` override fragment is order-dependent — I proved it fails; (b) `checkvintf --check-compat` needs the `/product` partition dirmap (or it reports four bogus `vendor.lineage.*` errors).

## Escalated

Untestable without an LTE tablet.
