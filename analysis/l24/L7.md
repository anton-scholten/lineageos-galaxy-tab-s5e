## 2. Root cause, with sources

`vendor/samsung/gts4lv-common/Android.bp:5` declares a `soong_namespace` importing seven namespaces. Six exist in the 24.0 tree; `hardware/qcom-caf/sdm845` does not. That file is generated by **our own** `device/samsung/gts4lv-common/extract-files.py:22`, which lists `'hardware/qcom-caf/sdm845'`.

**Upstream removal, identified exactly:** `LineageOS/android` commit **`a462d457ca85`** "manifest: Remove legacy repositories" (2026-06-21), `snippets/lineage.xml`. It deleted:

```
-  <project path="hardware/qcom-caf/sdm845/audio"   ... revision="lineage-23.2-caf-sdm845" />
-  <project path="hardware/qcom-caf/sdm845/display" ... revision="lineage-23.2-caf-sdm845" />
-  <project path="hardware/qcom-caf/sdm845/media"   ... revision="lineage-23.2-caf-sdm845" />
-    <linkfile src="os_pickup_qssi.bp" dest="hardware/qcom-caf/sdm845/Android.bp" />
```

(the same commit also removed `hardware/qcom-caf/msm8996` and `msm8998`)

CAF SoC list, 23.2 vs 24.0 (`.repo/manifests/snippets/lineage.xml` in each tree):

| | 23.2 | 24.0 |
|---|---|---|
| SoCs | msm8953 msm8996 msm8998 sdm660 **sdm845** sm8150 sm8250 sm8350 sm8450 sm8550 sm8650 sm8750 | msm8953 sdm660 sm8150 sm8250 sm8350 sm8450 sm8550 sm8650 sm8750 sm8850 |

23.2 manifest `snippets/lineage.xml:138-140` pinned the three sdm845 CAF repos at `lineage-23.2-caf-sdm845`. Those entries are gone in 24.0.

## 3. Why the import cannot simply be deleted

Cross-referenced every module name defined under the namespace against both the vendor blobs and our device tree. **22 modules are referenced**, e.g. `libqdutils`, `libOmxCore`, `libdrmutils`, `audio.primary.qcom`, `hwcomposer.qcom`, `libdisplaydebug`, `libsdmutils`.

- 7 are hard `shared_libs` link dependencies in the blobs. Example, `vendor/samsung/gts4lv-common/Android.bp:13525` `cc_prebuilt_binary mm-pp-dpps` → `shared_libs: [libcutils, libdisp-aba, libqdutils, ...]`.
- **None of the 22 resolve** from any other namespace present in the 24.0 tree. Checked `hardware/qcom-caf/common`, `hardware/qcom-caf/wlan`, `hardware/samsung`, `vendor/qcom/opensource` — all zero hits.
- Substituting another CAF SoC does not close the gap either: `sdm660` 19/22, `sm8250` 19/22, `sm8150` 20/22.

Deleting the import would therefore have moved the failure into the link step, not removed it. Not done.

## 5. The fix

New file **`local_manifests/24/caf-sdm845.xml`**, copied to `.repo/local_manifests/`. It pins the three CAF repos at `lineage-23.2-caf-sdm845` and restores the namespace linkfile.

The linkfile uses `<extend-project>` rather than `<project>`, because repo only accepts `<linkfile>` as a child of a project node and resolves `src` relative to that project's path. `extend-project` merges into the existing `hardware/qcom-caf/common` project, so upstream's own linkfiles for msm8953/sdm660/sm8150/... are preserved rather than restated here and going stale. Verified against `.repo/repo/manifest_xml.py` (`_ParseProject` handles `linkfile` children; the `extend-project` branch calls the same `_ParseLinkFile`).

This is a manifest entry, which TASKS-L24 §L7.2 lists as an allowed fix. It is not a shim, does not disable any check, and deletes no code.

## 7. Round 2: `libheif` removed from `frameworks/av`

Round 2 ran the same command, log `~/work/l24-build-2.log`, **2m00s**, exit 1, again at Soong bootstrap. The CAF error is **gone**: `PRODUCT_SOONG_NAMESPACES` in the log now contains `hardware/qcom-caf/sdm845`. Round 1's fix is confirmed working.

One new error:

```
error: vendor/samsung/gts4lv-common/Android.bp:12000:1: "libwfdcommonutils"
depends on undefined module "libheif".
```

**Cause.** `libheif` lived in `frameworks/av/media/libheif` in 23.2. In the 24.0 tree that path does not exist and no module named `libheif` is defined anywhere (only `imagedecoder_heif_fuzzer` remains). The 23.2 tree's build output confirms it was a real, built module: `all_modules.txt` lists `libheif` and `libheif_32`, and `out/target/product/gts4lvwifi/system/lib/libheif.so` exists.

**It cannot be deleted from the dependency list.** Unlike round 1, this is a genuine runtime dependency, not stale metadata:

```
$ llvm-readelf-19 -d proprietary/system_ext/lib/libwfdcommonutils.so | grep NEEDED
  (NEEDED)  Shared library: [libheif.so]     <- present, alongside libdng_sdk, libpiex, libjpeg, libpng
```

Dropping the line would produce a library that cannot load. `vendor/samsung/gts4lv-common/Android.bp` is byte-identical in both trees (`md5 e950c60b0112d57b691c99d80dd855f6`), so this is not drift on our side.

**Why 23.2 did not hit this:** it did not need to — `libheif` existed there. This is the same failure class as round 1, one layer down.

**What the module actually is** (`frameworks/av/media/libheif`, 56 KB): a single-source wrapper, `HeifDecoderImpl.cpp`, over `libmedia` + Skia's HEIF codec. It links only `libbinder`, `liblog`, `libutils`, `libmedia`. Every header it includes still exists in the 24.0 tree: `media/mediametadataretriever.h`, `media/stagefright/MediaSource.h`, `media/stagefright/foundation/ADebug.h`, `private/media/VideoFrame.h`, `drm/drm_framework_common.h`.

### Options, not yet chosen

| | Approach | Risk |
|---|---|---|
| A | Re-add the module to our tree as a local project (56 KB, 1 `.cpp`) | New C++ compiled against 24.0 platform internals — TASKS-L24 §3 marks blob ABI breaks 🔴 |
| B | Ship the already-built 23.2 `libheif.so` as a prebuilt blob | Stale binary; its `DT_NEEDED` is only stable platform libs, so it would likely load, but it is a shipped artifact that never gets rebuilt |
| C | Drop the dep and patch the blob | **Rejected.** `libheif.so` is in `DT_NEEDED`; the result cannot load |

Owner chose **A** (re-add the module). Two commits on `anton-scholten/android_device_samsung_gts4lv-common`
branch **`port/l24-dt-2`**, cut from the L6 port state `5af53f1`. `lineage-24.0` untouched.

| Commit | Change |
|---|---|
| `495967f` | `libheif/` — 4 files, +1119. Sources copied **verbatim** from the 23.2 tree |
| `0c5823a` | `libshim_wfdservice`: AIDL `types-V4-cpp` → `V5-cpp` (round 4, below) |

**Where it lives, and why.** `frameworks/av/media/libheif` is a path *inside* a project we do not fork.
Reverting `android_frameworks_av` to 23.2 to recover 56 KB would undo the entire Android 17 media port.
Instead the module sits in our device tree, whose `soong_namespace` (`device/samsung/gts4lv-common`)
is **already imported** by `vendor/samsung/gts4lv-common/Android.bp:7`. The blob resolves it with no
manifest change.

Two details verified rather than assumed:
- The original `package{}` block selected `frameworks_av_license`, declared by `android_frameworks_av` and
  undefined here — dropped.
- No `include_dirs` needed. `drm/drm_framework_common.h` and `private/media/VideoFrame.h` resolve via
  `commonGlobalIncludes` at `build/soong/cc/config/global.go:553`, applied to every cc module. Confirmed the
  list is unchanged in 24.0.

## 7b. Round 3→4: `libshim_wfdservice` AIDL version split

Round 3 confirmed `libheif` resolved (its error is gone) and hit a **new** error, this time in our own code:

```
error: device/samsung/gts4lv-common/shims/libwfdservice/Android.bp:6:1:
module "libshim_wfdservice" variant "android_arm_armv8-a_shared": depends on
multiple versions of the same aidl_interface:
android.media.audio.common.types-V4-cpp-source, android.media.audio.common.types-V5-cpp-source
```

**Cause.** The shim pinned `android.media.audio.common.types-V4-cpp`. 24.0 moved the platform to V5, so
`libmedia_headers` now resolves `av-types-aidl-cpp` → V5, while the shim still asked for V4. Soong refuses a
module pulling two versions of one AIDL interface. The error's own dependency path shows both routes.

**The bump is safe, and that was checked rather than assumed.** `AudioPort.aidl` — the only type
`AudioSystem.cpp` names — is **byte-identical** between v4 and v5:

```
diff .../aidl_api/android.media.audio.common.types/4/android/media/audio/common/AudioPort.aidl \
     .../aidl_api/android.media.audio.common.types/5/android/media/audio/common/AudioPort.aidl
-> no differences
```

so the mangled symbol the shim defines
(`_ZN7android11AudioSystem24setDeviceConnectionStateE24audio_policy_dev_state_tRKNS_5media5audio6common9AudioPortE14audio_format_t`)
is unchanged, and the forward to the 4-argument `setDeviceConnectionState` still matches. The rest of V5 is
purely additive (new `Ambisonics` parcelable, new `AudioDeviceType`/`AudioUsage`/`AudioProductStrategyType`
enumerants, two new `.aidl` files); none of it is reachable from this shim.

This is a **renamed Soong module** dependency, allowed by TASKS-L24 §L7.2.

## 7c. Round 4→5: the same AIDL split, in a blob

Round 3's fix worked — `libshim_wfdservice` no longer appears. Round 4 failed with the **same class** of
error, one module further on:

```
error: vendor/samsung/gts4lv-common/Android.bp:12749:1:
module "libwfdservice" variant "android_arm_armv8-a_static": depends on
multiple versions of the same aidl_interface:
android.media.audio.common.types-V4-cpp-source, V5-cpp-source
```

The dependency path in the error is the whole story:
`libwfdservice → libwfdsinksm → libwfdrtsp → libwfdcommonutils → libheif → libmedia → libaudiobase`.
The V5 arrives through the `libheif → libmedia` edge that round 3's fix opened; the V4 is the blob's own pin.

**Two repos had to change together**, which is why this is one logical fix in two commits:

| Repo | Branch | Commit | Change |
|---|---|---|---|
| `android_device_samsung_gts4lv-common` | `port/l24-dt-3` | `fea70cd` | `extract-files.py:50` rewrite target V2→V4 becomes V2→**V5** |
| `proprietary_vendor_samsung_gts4lv-common` | `port/l24-vendor-1` | `fd677bb` | `Android.bp:12776` V4-cpp → V5-cpp, **and** the blob's `DT_NEEDED` string patched V4→V5 |

**The binary had to be patched, not just the metadata.** Soong is satisfied by the `Android.bp` change
alone, but the ELF would still name `android.media.audio.common.types-V4-cpp.so`, which 24.0 does not ship —
so the loader would fail at runtime on a build that looked clean. That is the failure mode to watch for on
every future blob rename.

Verified before committing:
- `V4-cpp.so` and `V5-cpp.so` are both **42 bytes**, so the in-place patch moves no offsets.
- The string occurs **exactly once** in the file.
- File is **178905 bytes before and after**; `llvm-readelf-19` still parses it and reports the new `NEEDED`.
- Only the 32-bit blob exists; there is no `lib64` variant. A copy of the original blob was kept at
  `/tmp/opencode/libwfdservice.so.bak` (outside the tree).
- `extract-files.py` kept at **V2→V5**, not V4→V5: that line documents the transformation applied to the
  original TheMuppets blob, which needs V2. The committed blob was already patched and went V4→V5.

This is a **blob fixup that renames a dependency**, explicitly allowed by TASKS-L24 §L7.2. No code is
disabled and no symbol is stubbed — the blob still imports exactly the symbols it imported before, because
`AudioPort.aidl` is byte-identical between v4 and v5.

### Pattern worth naming

Two consecutive blockers, both the same shape: **Android 17 removed platform code that 22.2-era vendor blobs still link against.** Round 1 was CAF (sdm845), round 2 is `frameworks/av` (`libheif`). Expect more of the same. The real risk in this port is not FCM 7 or the device tree — it is the age gap between the blobs (22.2) and the platform (24.0). `review-L1-L3.md` did not anticipate this because it compared device trees, not blob link dependencies.

## Problems

1. **First sync attempt failed**: `error: no fetch in <remote>`. Cause: the manifest declared `<remote name="github" />` with no `fetch` attribute, which *replaces* the inherited remote from `default.xml:4` instead of merging. Fixed by removing the declaration and inheriting.
2. **First draft of the manifest used a top-level `<linkfile>`**, which repo ignores — `<linkfile>` is only parsed as a child of a `<project>` node. Fixed with `<extend-project>` before anything was synced.
3. **Log is empty for minutes at a time.** `repo` and the build both block-buffer when stdout is not a TTY (`L4.md` §5). Not a hang; judge by directory growth and `.repo/project-objects` count.
