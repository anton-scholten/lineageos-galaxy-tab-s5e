# L1: reference-tree changes 23.2 -> 24.0

All observations below were made on **2026-10-09** with `gh 2.46` against `github.com/LineageOS/*` and
`github.com/ExyHyperBrick/*`, and against our own tree at `/home/anton/android/lineage/device/samsung/gts4lv-common`
(`1188e2b14a5a`, branch `lineage-23.2`). Confidence levels are per item.

## Summary

97 commits sit on the `lineage-24.0` side of the five reference repos; 1 is ignored by the step-2 rule, so
`L1-changes.tsv` has **96 data rows** (97 lines with the header) — self-check in §Self-check.
Only **6** commits are `yes` and **9** are `unsure`; the rest are `no`.
**Nothing here needs a kernel change.** Our kernel is 5.15.178 with `CONFIG_HIDRAW=y`, already above what
sm7125 had to reach for 24.0 (5.10.239), so the `ro.bpf.kver_override` bump is `no`.

same Change-Ids we already have on 23.2 — so most of that repo's list is a no-op for us, not a change.
`lineage-24.0` is still moving (frameworks/base took 165 commits in the last 30 days), so §Findings likely to change
before an official release is called out explicitly at the end.

## 4. Does anything here require a KERNEL change? — No

**Answer: no. Nothing in this task's list asks for a kernel change, and the one commit that looks like it does is `no`.**

The commit that looks like a kernel requirement is sm7125 `e1549c202db5`, "Bump kernel BPF version override to
5.10.239", `ro.bpf.kver_override=5.4.299 -> 5.10.239`. Reason it is `no` for us:

1. Our override is already higher. `product.prop:7` = `ro.bpf.kver_override=5.15.178` @ `1188e2b`.
2. 5.15 is an explicitly supported value, so nothing needs bumping.
   `LineageOS/android_packages_modules_Connectivity` `bpf/headers/include/bpf/KernelUtils.h:105` @ `ab21b78a1812`
   (`bpf: Allow overriding kernel version`, 2025-07-07; `lineage-24.0` head `7c04d866538e`) lists
   `isKernelVersion(5, 15)  // first supported in Android T`. The override is read at `KernelUtils.h:39` and
   parsed into `kernelVer`, so it must be a version the loader supports, and 5.15 is.
3. The sm7125 bump was forced by *their* kernel: it is 4.14 (`FEASIBILITY-LINEAGE-24.md` evidence row, and
   `android_kernel_samsung_sm7125` `lineage-23.2...lineage-24.0` = **1531 commits ahead, 0 behind**). Those 1531
   commits are how they got their 4.14 tree to behave like a 5.10 one. Our tree is a real 5.15.
4. `PRODUCT_OTA_ENFORCE_VINTF_KERNEL_REQUIREMENTS` (`1d2a05927c04`) is the *other* commit that reads like a kernel
   workaround. sm7125's message is literally "Until we fix kernel". That flag exists because their kernel lacks the
   FCM-7 kernel requirement. Our `arch/arm64/configs/gts4lv_defconfig:464` has `CONFIG_HIDRAW=y` and `:823`
   `CONFIG_USERFAULTFD=y`; sm7125 had to add `CONFIG_HIDRAW=y` to `lineage-a72q_defconfig` on 24.0 (their 23.2
   defconfig had `# CONFIG_HIDRAW is not set`). We already have it. Keep the flag out unless L7 fails.

Confidence: **high** for points 1-4. The one thing I did not verify is whether the 24.0 `check_elf_file` /
kernel-requirements path adds a *new* requirement beyond HIDRAW — that is exactly what L7's first build will tell us.

Kernel-side reference data points for L5-L7:

- `android_kernel_samsung_sm7125`: `lineage-23.2...lineage-24.0` ahead_by=1531, behind_by=0.
- `android_kernel_motorola_exynos9610`: `lineage-23.2...lineage-24.0` **ahead_by=0, behind_by=0**. Zero kernel
  commits for 24.0. This is the strongest evidence that a legacy kernel can do 24.0 with device-tree work only.
