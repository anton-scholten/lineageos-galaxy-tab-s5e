## Why it conflicts
merge-tree on its own (`git merge-tree --write-tree --merge-base=880ea49bde40^ a30605a54f3b 880ea49bde40`, tree
`d330a361b15f66ef1cecb6c0ac880ec86eb9e055`) reports exactly one content conflict, in one block. Not a
stacked-replay artefact.

- Block 1, mm/userfaultfd.c ~line 366-386 of the merged file, inside `__mcopy_atomic()` just after the dst-vma
  bounds checks: ours (sdm670) = a CAF hardening comment *"Check the vma is registered in uffd, this is required to
  enforce the VM_MAYWRITE check done at uffd registration time."* and nothing else; theirs (series) = the comment
  *"If this is a HUGETLB vma, pass off to appropriate routine"* plus the 3-line early
  `if (is_vm_hugetlb_page(dst_vma)) return __mcopy_atomic_hugetlb(dst_mm, dst_vma, dst_start, src_start, len, zeropage);`
  and then the comment *"Be strict and only allow __mcopy_atomic on userfaultfd registered ranges..."*. Both sides then
  fall through to the same common code `if (!dst_vma->vm_userfaultfd_ctx.ctx) goto out_unlock;`
  (`mm/userfaultfd.c:191` @ `a30605a54f3b`). In other words: same code, two different comments - the actual added
  behaviour is the hugetlb pass-off, and CAF's comment belongs to the line that follows in both trees.
- The rest of the commit (183 lines of new `#ifdef CONFIG_HUGETLB_PAGE` function plus the two `#include`s
  `<linux/hugetlb.h>` / `<linux/pagemap.h>`) applies cleanly.

Two things not to "fix" while merging:
- Do **not** change the early `return __mcopy_atomic_hugetlb(...)` into `goto out_unlock`. The new function's own
  comment says "called with mmap_sem held, it will release mmap_sem before returning", and every one of its return
  paths does `up_read(&dst_mm->mmap_sem)` itself. This matches upstream 60d4d2d2b40e.
- Order matters: the hugetlb pass-off must stay **above** `if (!dst_vma->vm_userfaultfd_ctx.ctx)`, which is upstream's
  order, and is also what keeps CAF's uffd-registration enforcement for normal pages.

Build risk the lead must know about (does not show up as a conflict): the new function calls three helpers that
**sdm670's arm64 tree does not have**. `git grep` in `a30605a54f3b`:
- `hugetlb_mcopy_atomic_pte` -> MISS (present in the Exy tree at `include/linux/hugetlb.h` and `mm/hugetlb.c`)
- `copy_huge_page_from_user` -> MISS (present in the Exy tree at `include/linux/mm.h`, `mm/hugetlb.c`, `mm/memory.c`)
- `huge_pte_size` -> MISS everywhere, including `baa585f67e0e` (it is an x86-only helper in 4.9; arm64 uses
  `huge_page_size(h)`, which sdm670 does have)

The first two are supplied by two earlier series commits, both CLEAN in `analysis/exyhyperbrick-trial/results.tsv`:
- `372b8197c632` "UPSTREAM: hugetlb: add copy_huge_page_from_user" (`include/linux/mm.h`, `mm/memory.c`)
- `e988f46067f3` "UPSTREAM: hugetlb: add hugetlb_mcopy_atomic_pte for userfaultfd support"
  (`include/linux/hugetlb.h`, `mm/hugetlb.c`)
Both are ancestors of `880ea49bde40^`, so in the stacked replay they are already in place. The third one
(`huge_pte_size`) is never supplied by anyone - it is only harmless because `CONFIG_HUGETLB_PAGE` is not enabled in
the gts4lv defconfigs (`git show a30605a54f3b:arch/arm64/configs/gts4lv_defconfig | grep -i hugetlb` -> no hits; the
Exy arm64 defconfigs do not set it either), so the whole block is `#ifdef`'d out.

the same shape the patch expects, but no hugetlb path at all.
## Proposed resolution
MERGE: keep both sides' text - the hugetlb pass-off block from the series (3 code lines + its comment) **and** sdm670's
CAF comment, in that order, so the result is: hugetlb check -> CAF comment -> `if (!dst_vma->vm_userfaultfd_ctx.ctx)`.
Take the rest of the file from the series unchanged. Do not renumber or drop the early `return` (see above).

Conditional note for the lead: this commit is only safe while `CONFIG_HUGETLB_PAGE` stays off. If you ever turn
hugetlbfs on for arm64 you must also replace `huge_pte_size(h)` with an arm64 equivalent and add the two helper
commits - and `hugetlb_mcopy_atomic_pte()` in `mm/hugetlb.c` is x86-flavoured upstream too, so expect more work there.
None of this blocks the eBPF/boot goal.
