## Why it conflicts
merge-tree on its own: **conflicts** (4 blocks, all in `fs/userfaultfd.c`; tree `ace6b134cf80`).

Root cause: sdm670's `userfaultfd_register()`/`userfaultfd_unregister()` reject every non-anonymous VMA with the
**4.9-era test `cur->vm_ops`** (`fs/userfaultfd.c:840`, `:1010` @ a30605a54f3b), and sdm670 additionally has an
upstream `VM_MAYWRITE` gate that the Exy series base does *not* have. The series commit's context lines are
`!vma_is_anonymous(cur)` (series base `fs/userfaultfd.c:1132` @ f0f30b4639c2^). So this is a *fork-rewrite* conflict,
not a "commit already applied" conflict.

- Block 3, fs/userfaultfd.c ~line 1063 (`userfaultfd_unregister`, VMA scan):

Both helpers the commit needs already exist in sdm670 4.9:
- `is_vm_hugetlb_page()` — `include/linux/hugetlb_inline.h:8` and `:15` @ a30605a54f3b (pulled in by `hugetlb.h:7`).
- `vma_kernel_pagesize()` — `include/linux/hugetlb.h:394` @ a30605a54f3b.
- `vma_is_anonymous()` — `include/linux/mm.h:1534` @ a30605a54f3b (it is `!vma->vm_ops`, so `!vma_is_anonymous(x)` == `x->vm_ops`).

## Proposed resolution
MERGE — per block, keep sdm670's surrounding code and substitute the hugetlb-aware test:
- Block 1: keep ours' 9-line UFFDIO_COPY/VM_MAYWRITE comment + `ret = -EPERM;` + the VM_MAYWRITE check unchanged;
  change only the first line to the hugetlb-aware form. sdm670 is free to use either spelling:
  `if (!vma_is_anonymous(cur) && !is_vm_hugetlb_page(cur))` or the 4.9 form
  `if (cur->vm_ops && !is_vm_hugetlb_page(cur))` — they are identical, and the first one is what the following
  commits in this batch expect.
- Block 2: replace `BUG_ON(vma->vm_ops);` with `BUG_ON(!vma_is_anonymous(vma) && !is_vm_hugetlb_page(vma));`.
  Keep ours' following `BUG_ON(vma->vm_userfaultfd_ctx.ctx && ...)` and `WARN_ON(!(vma->vm_flags & VM_MAYWRITE));`.
- Block 3: same substitution as block 1, on the single line (no VM_MAYWRITE block here).
- Block 4: same substitution as block 2, and **keep sdm670's `WARN_ON(!(vma->vm_flags & VM_MAYWRITE));` line**
  — moving that WARN_ON is the job of b07d07e8f011 in this batch, not of this commit.

Take the `include/uapi/linux/userfaultfd.h` auto-merge as-is (it only inserts `UFFD_API_RANGE_IOCTLS_HPAGE`
after `UFFD_API_RANGE_IOCTLS`, which sdm670 has at `include/uapi/linux/userfaultfd.h:25`).

No `vma_merge()` guard is needed: hugetlb VMAs carry `VM_SPECIAL`, and `__vma_merge()` bails out immediately on
it (`mm/mmap.c:1184-1185` @ a30605a54f3b), so the unconditional `vma_merge()` call in the apply loop is safe.

**Risk note for the human (optional group):** `gts4lvwifi_defconfig` @ a30605a54f3b sets neither
`CONFIG_HUGETLB_PAGE` nor `CONFIG_HUGETLBFS`. With `CONFIG_HUGETLB_PAGE=n` sdm670 compiles `is_vm_hugetlb_page()`
to `false` (`include/linux/hugetlb_inline.h:14-19`) and `vma_kernel_pagesize(v)` to `PAGE_SIZE`
(`include/linux/hugetlb.h:515`), so after this merge the new code is **inert unless K6 also adds
`CONFIG_HUGETLB_PAGE`**. A DROP here therefore loses very little on today's defconfig — but it would silently
drop the feature for anyone who later enables HUGETLB, so MERGE is still the right call.
