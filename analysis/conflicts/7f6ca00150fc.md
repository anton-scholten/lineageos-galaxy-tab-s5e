## Proposed resolution
MERGE: keep sdm670's `clang-android.sh` error check **and** add theirs' two lines,
with the order below (the `endif` before the vendor check, not after it):
```
CLANG_TRIPLE	?= $(CROSS_COMPILE)
ifneq ($(CLANG_TRIPLE),)
CLANG_FLAGS	+= --target=$(notdir $(CLANG_TRIPLE:%-=%))
endif
ifeq ($(shell $(srctree)/scripts/clang-android.sh $(CC) $(CLANG_FLAGS)), y)
$(error "Clang with Android --target detected. Did you specify CLANG_TRIPLE?")
endif
ifneq ($(CROSS_COMPILE),)
```
Order matters and is the only judgement here. scripts/clang-android.sh tests
`__ANDROID__` on the compiler named in `$(CC)`, with `$(CLANG_FLAGS)` passed
through, so its purpose is to turn a silently-wrong-target build into a loud
error. If you nest the check *inside* the new `ifneq ($(CLANG_TRIPLE),)` block,
the check stops running exactly when `CLANG_TRIPLE` is unset — the case it exists
to catch — and the safety net is silently lost. Placing it after the `endif`
keeps sdm670's current behaviour unchanged: the check always runs, and it still
sees the `--target=` that was just appended.
Impact is nil for our build: this whole block is inside `ifeq ($(cc-name),clang)`
and the LineageOS 23.2 kernel build uses the GNU toolchain, so `cc-name` is never
clang. Build tooling only, no runtime effect.
