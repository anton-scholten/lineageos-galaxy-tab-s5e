## Why it conflicts
merge-tree on its own: **conflicts** (tree `1839a0a8e56a`).

The real reason sdm670 and the series disagree is that **sdm670's `madvise_dontneed()` is still the original
4.9 form**, while the Exy tree already has the 4.11-era `madvise_dontneed_free()`:

- sdm670: `madvise_dontneed()` = `can_madv_dontneed_vma()` + a direct
  `zap_page_range(vma, start, end - start, NULL)` (`mm/madvise.c:476-485` @ a30605a54f3b). No
  `userfaultfd_remove()` revalidation, no `madvise_dontneed_single_vma()`.
  `git grep -n 'userfaultfd_remove\|madvise_dontneed_single_vma\|madvise_dontneed_free' a30605a54f3b -- mm/`
  → no hits.
- series base: `madvise_dontneed_free()` with `userfaultfd_remove()`, `madvise_dontneed_single_vma()` and
  `madvise_free_single_vma()` (`e8212ce13516` @ 138179e5ccba^).

This commit's third madvise.c hunk is a *rename* of the VMA predicate inside that function, which sdm670 simply
does not have — hence the conflict.

Per block:

- Block 1, mm/madvise.c ~line 13 (includes): ours = nothing extra; theirs = `page_idle.h` + `userfaultfd_k.h`.
  Take theirs. Both headers exist in sdm670 (`include/linux/page_idle.h`,
  `include/linux/userfaultfd_k.h` @ a30605a54f3b).
- Block 2, mm/madvise.c ~line 654 (`madvise_dontneed()` body): ours = 4 lines,
  `if (!can_madv_dontneed_vma(vma)) return -EINVAL;` + `zap_page_range(vma, start, end - start, NULL);`
  (`mm/madvise.c:481-483` @ a30605a54f3b);
  theirs = the whole ~50-line `madvise_dontneed_free()` body (`userfaultfd_remove()` revalidation loop plus
  dispatch to `madvise_dontneed_single_vma()` / `madvise_free_single_vma()`).
  **Take ours verbatim.** This commit only wants `can_madv_dontneed_vma` → `can_madv_lru_vma` renamed in this
  function; the rest of theirs is a feature from commits sdm670 does not have. Adopting it would introduce a
  call to `userfaultfd_remove()`, which does not exist in sdm670.
- Block 3, mm/internal.h ~line 66: ours = `static inline bool can_madv_dontneed_vma(struct vm_area_struct *vma)`
  (`mm/internal.h:66` @ a30605a54f3b); theirs = the identical helper renamed to `can_madv_lru_vma`.
  The **body is byte-identical on both sides** (`return !(vma->vm_flags & (VM_LOCKED|VM_HUGETLB|VM_PFNMAP));`,
  `mm/internal.h:67-68` @ a30605a54f3b) — only the name differs. This is sdm670 already carrying the same
  change under the old name.
- Blocks 4-7, the four uapi `mman.h` files: ours = ends at `MADV_DODUMP 17`; theirs = `MADV_WIPEONFORK 18`,
  `MADV_KEEPONFORK 19`, `MADV_COLD 20`. Take theirs (`MADV_COLD` **must** be 20 — the number is ABI).
  See the ordering note above: prefer to have 7b1c5c0a4417 applied first so only `MADV_COLD 20` is added.

Everything else applied cleanly and is what the commit is really for: `case MADV_COLD:` in
`madvise_need_mmap_write()`, `madvise_vma()` and `madvise_behavior_valid()`, plus the new
`madvise_cold_pte_range()` / `madvise_cold_page_range()` / `madvise_cold()` functions (result tree
`mm/madvise.c:272`, `:405`, `:420`, `:812`, `:842`).

## Already in sdm670?
**partly.** The MADV_COLD feature is absent, but the helper this commit renames is already there.

- `git grep -n 'MADV_COLD' a30605a54f3b` → no hits (checked whole tree).
- `git grep -n 'madvise_cold' a30605a54f3b` → no hits.
- `git grep -n 'can_madv_lru_vma' a30605a54f3b` → no hits.
- `git grep -n 'can_madv_dontneed_vma' a30605a54f3b -- mm/` → **2 hits**: definition `mm/internal.h:66`,
  one use `mm/madvise.c:481`. So the rename touches exactly those two lines.
- `git log a30605a54f3b --grep='introduce MADV_COLD' -F` → no match; upstream `9c276cc65a58` not in history.

Everything the new code calls already exists in sdm670 4.9, verified by grep:
`pmdp_invalidate` (`include/asm-generic/pgtable.h:253`), `tlb_remove_pmd_tlb_entry`
(`include/asm-generic/tlb.h:231`), `flush_tlb_batched_pending` (`mm/internal.h:517`),
`arch_enter_lazy_mmu_mode` (`include/asm-generic/pgtable.h:487`), `ptep_get_and_clear_full`
(`include/asm-generic/pgtable.h:149`), `deactivate_page` (`include/linux/swap.h:311`),
`test_and_clear_page_young` (`include/linux/page_idle.h:21`), and `struct mm_walk` already has the
4.9-style flat `pmd_entry` / `mm` / `private` members the new initialiser uses
(`include/linux/mm.h`, `struct mm_walk { ... int (*pmd_entry)(...); ... void *private; }` @ a30605a54f3b).
So krazey's "use the 4.9 page walker" adaptation is already satisfied on our side.

## Proposed resolution
MERGE — 3 blocks on `mm/madvise.c` + `mm/internal.h` as described above, plus (if 7b1c5c0a4417 has not been
applied yet) take-theirs on the four uapi `mman.h` blocks.

The one decision the human must make consistently:

> **Rename sdm670's `can_madv_dontneed_vma` → `can_madv_lru_vma`.** Do it in exactly two places
> (`mm/internal.h:66` definition and `mm/madvise.c:481`), then take theirs in the `mm/internal.h` conflict block
> (or equivalently keep ours' name and change the *three* `can_madv_lru_vma` call sites the commit introduced
> back to `can_madv_dontneed_vma` at result-tree `mm/madvise.c:428`, `:655`/`:661`, `:683`).
> Getting this wrong leaves an undefined-function compile error, not a silent miscompile — the second option is
> the lower-risk one if in doubt, because the body is identical either way.

Do **not** take theirs' `madvise_dontneed()` body: `userfaultfd_remove()` does not exist in sdm670.

**Value note (optional group):** a DROP here loses a genuine, desirable tweak — MADV_COLD lets Android 16's
`lmkd`/ActivityManager mark cached-app pages cold without swapping them, which is the whole point of the
backport. It is *not* required for eBPF or boot, so if the human wants to cut risk, this is a defensible drop —
but it should be a deliberate decision, and the sdm670-only helper rename must then be left alone.

Side effect to be aware of if 7b1c5c0a4417 has not been applied yet: taking theirs on the uapi headers adds
`MADV_WIPEONFORK 18` / `MADV_KEEPONFORK 19` **without** the matching `madvise_behavior()` cases, so
`madvise(MADV_WIPEONFORK)` would return `-EINVAL`. Harmless, but apply 7b1c5c0a4417 first and this disappears.
