## Already in sdm670?

**No.** The commit rewrites the body of `__run_hrtimer()`, which does exist
(`kernel/time/hrtimer.c`, 4 sites, plus its prototype in `include/linux/hrtimer.h`), but the
irqsave/irqrestore protection it adds around that body is not present in sdm670.

Function presence is not change presence: the existing `__run_hrtimer()` is the *pre-change* version.

## Proposed resolution
MERGE: in every one of the 4 blocks keep **both** - the Samsung `debug_timestamps` line from ours and the
irqsave/irqrestore call from theirs. Concretely:

| Block | Result |
|---|---|
| 1 | `tmp[4] = sched_clock();` **then** `raw_spin_unlock_irqrestore(&cpu_base->lock, flags);` |
| 2 | `raw_spin_lock_irq(&cpu_base->lock);` **then** `tmp[7] = sched_clock();` |
| 3 | `tmp = this_cpu_ptr(debug_timestamps);` + `tmp[0] = sched_clock();` **then** `raw_spin_lock_irqsave(&cpu_base->lock, flags);` |
| 4 | `tmp[8] = sched_clock();` **then** `raw_spin_lock_irqsave(&cpu_base->lock, flags);` |

Do **not** drop the `tmp[]` lines: `tmp` is `this_cpu_ptr(debug_timestamps)`
(`kernel/time/hrtimer.c:1341` @ a30605a54f3b, array declared at `kernel/time/hrtimer.c:100`), snapshotted at
`kernel/time/hrtimer.c:1436-1437` for Samsung's boot-timing debug, and `tmp[5]`/`tmp[6]`/`tmp[7]` sit between the
two lock ops, so the array must keep being filled.

⚠️ Check order in blocks 1 and 3: keep the `sched_clock()` read *outside* the freshly-taken lock, i.e. exactly as
listed above, so the measured timestamps keep their current meaning.

No caller is missed: sdm670 has exactly two `__hrtimer_run_queues()` call sites (`kernel/time/hrtimer.c:1355`,
`:1468` @ a30605a54f3b) and both are in the auto-merged part of the tree, so adding the parameter compiles.
This is a **prerequisite** for `2c3ab8405d6a` (softirq-based hrtimers need interrupts enabled around the callback).
