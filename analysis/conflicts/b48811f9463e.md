## Proposed resolution
MERGE:  — take *theirs* for block 1 in full; nothing of *ours* in that block needs preserving, because the
only line we have (`__pm_wakeup_event(ws, 2 * MSEC_PER_SEC);`) is exactly the line theirs replaces.

Two things the lead must know before taking theirs:

1. **`CONFIG_SEC_PM_DEBUG` is enabled in our build**, so the new `#ifdef` block is compiled in, not dead
   code: `CONFIG_SEC_PM_DEBUG=y` at `arch/arm64/configs/gts4lvwifi_defconfig:788` and
   `arch/arm64/configs/gts4lv_defconfig:790` (also both `*_eur_open` defconfigs). The symbol is defined in
   `arch/arm64/Kconfig.debug` at `a30605a54f3b`. Consequence: the new `pr_err` will really print, and it
   uses `%u` with `wake_ms` (`unsigned int`) — correct.
2. **Variable shadowing.** sdm670 already declares `uint64_t msec = 0;` at function scope under
   `#ifdef CONFIG_SEC_PM_DEBUG` (`kernel/time/alarmtimer.c:354-356 @ a30605a54f3b`). The patch's inner
   `s64 msec = ktime_to_ms(min);` shadows it inside the `if` block. This compiles (the kernel does not build
   with `-Wshadow`) and is not a bug — the outer `msec` is used later at `kernel/time/alarmtimer.c:397`
   outside the block — but if the lead prefers a warning-free tree, rename the inner one to `wake_msec`.
   That is an optional cosmetic edit, not required for correctness.

Behaviour check for the lead: the new logic is self-consistent. For an alarm already expired it holds the
wakeup source 1 ms; for an alarm *t* ms away it holds *t*+1 ms, capped at the original 2000 ms — so the
wakeup never ends before the alarm it is waiting for. Nothing else in the tree depends on the constant
`2 * MSEC_PER_SEC` here, and the only later series commit touching this file,
`0c6f8a9a50ad` "BACKPORT: PM / wakeup: Show wakeup sources stats in sysfs", edits a different hunk
(`wakeup_source_register()` call in `alarmtimer_init()`, ~line 961).

This is an optional power tweak (batch group `optional`): keeping it is a judgement call, and dropping it
would only lose the shorter wakeup hold, i.e. slightly worse battery drain on the rare "alarm too close to
suspend" path. Nothing breaks either way.
